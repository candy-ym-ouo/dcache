# 01 项目概述与需求分析

## 1. 项目背景与目标

随着单机缓存（如进程内 map 缓存）在数据量、并发与可用性上的瓶颈凸显，分布式缓存成为水平扩展的标准解法。本项目的目标是用 **Go 标准库**（零第三方依赖）从零实现一个可演示、可运行、可扩展的分布式缓存服务 **DCache**，覆盖分布式缓存的关键机制：

- **一致性哈希**：解决节点增减时大量 Key 失效（rehash 风暴）的问题；
- **TCP 协议**：提供高性能的二进制网络通信，不依赖 HTTP 开销；
- **TTL 过期**：支持带生命周期的缓存数据；
- **LRU 淘汰**：控制单节点内存上限；
- **多节点分片**：数据按 Key 分布到多个节点；
- **节点增减时的数据迁移**：扩容/缩容时自动迁移受影响数据，保证数据可达性。

**项目定位**：教学与工程演示级分布式缓存。强调"机制完整、逻辑清晰、代码规模可控"（Go 代码 2000~2200 行、20~25 个文件），并附带一个简单 Web 控制台用于可视化运维演示。

## 2. 需求来源与拆解

原始提示词拆解为六条核心需求：

| 编号 | 需求 | 关键词 |
| --- | --- | --- |
| R1 | 用 Go 实现缓存服务 | 语言约束：Go，标准库 |
| R2 | 基于一致性哈希 | 分片路由：哈希环、虚拟节点 |
| R3 | 支持 TCP 协议 | 自定义二进制协议，长连接 |
| R4 | TTL 过期 | 惰性 + 主动清扫 |
| R5 | LRU 淘汰 | 容量约束、淘汰策略 |
| R6 | 多节点分片 + 节点增减时的数据迁移 | 集群管理、迁移流程 |

## 3. 功能清单（扩写）

在核心需求之上，扩写为以下功能模块：

### 3.1 基础 KV 操作（F1）
- `SET key value [EX seconds]`：写入键值对，可选 TTL；
- `GET key`：读取键值；不存在或已过期返回空；
- `DEL key`：删除键；
- `EXISTS key`：判断键是否存在（未过期）；
- `KEYS [prefix]`：按前缀列出键（用于控制台浏览与调试）；
- `FLUSH`：清空本节点全部数据。

### 3.2 TTL 生命周期管理（F2）
- `EXPIRE key seconds`：为已存在的键设置/重置过期时间；
- `TTL key`：查询剩余存活秒数（-1 表示永不过期，-2 表示键不存在）；
- `PERSIST key`：移除过期时间，使键永不过期；
- 过期语义：**惰性删除**（访问时校验）+ **主动清扫**（后台定时器扫描，避免过期键长期占用内存与 LRU 槽位）。

### 3.3 LRU 内存淘汰（F3）
- 每节点配置容量上限（键数量上限 + 可选字节数上限）；
- 写入新键且容量已满时，淘汰**最久未使用**的条目；
- 访问（GET/EXISTS）会刷新条目"最近使用"状态；SET 覆盖同样刷新；
- TTL 清扫腾出的空间立即归还容量。

### 3.4 一致性哈希分片与路由（F4）
- 哈希环：CRC32 哈希 + 每节点 160 个虚拟节点（可配置），保证均衡性与单调性；
- 路由位置：**客户端路由**为主 —— Go 客户端本地维护节点列表与哈希环，直接定位目标节点；
- 兜底机制：**服务端归属校验** —— 节点收到不属于自己的 Key 请求时，返回 `MOVED <node>` 重定向，兼容"客户端环视图过期"或第三方直连的场景。

### 3.5 集群与节点管理（F5）
- 节点注册：新节点通过 `-seed` 参数向已有节点发起 JOIN，广播至全集群；
- 节点列表维护：每个节点维护一致的集群视图（成员表）；
- 节点下线：支持**优雅下线**（LEAVE：先迁移、再退出）与**故障剔除**（心跳超时后被成员表移除）；
- 控制命令：`INFO`（节点自身信息）、`STATS`（指标）、`MEMBERS`（成员表）。

### 3.6 数据迁移（F6）
- 触发时机：节点加入（扩容）或节点离开（缩容/剔除）导致哈希环变化后；
- 迁移范围：仅迁移**归属发生变化的 Key**（数量约为 `K/N`），而非全量数据；
- 迁移机制：源节点扫描本地存储 → 按新环计算归属 → 将不属于自己的 Key 分页批量发送至新归属节点；
- 迁移保障：幂等写入（SET 语义）、保留剩余 TTL、进度可查询、环再次变化时自动中止并重算、节点宕机后可续传。

### 3.7 心跳与健康检查（F7）
- 每节点周期（默认 1s）向集群内其他节点发送 PING；
- 连续 N 次（默认 3 次）未收到 PONG 判定为故障；
- 故障节点从成员表剔除并触发环重建与数据迁移决策。

### 3.8 TCP 协议与 Go 客户端（F8）
- 自定义二进制协议：定长头部（命令、键长、值长、TTL 等）+ 变长负载；
- 支持粘包/拆包、半包读取；响应携带状态码与错误信息；
- Go 客户端：连接池（每节点多连接）、请求-响应配对（序号）、自动路由与 MOVED 跟随重定向、超时控制。

### 3.9 Web 控制台（F9）
- 简单前端：原生 HTML/CSS/JS，由 Go `embed` 内嵌并通过 HTTP 服务；
- 功能：集群拓扑与节点健康、缓存指标（命中率/QPS/容量）、键浏览与操作、节点添加/下线（触发真实迁移）、迁移进度可视化、命令测试台。

### 3.10 指标与日志（F10）
- 指标：总键数、读写次数、命中/未命中、命中率、淘汰数、过期清扫数、迁移字节数/键数/进度、节点状态；
- 日志：结构化文本日志（时间戳、级别、模块、事件），支持 `-log-level` 配置。

## 4. 核心业务逻辑（详细流程）

### 4.1 写流程：SET

```
客户端 → 路由层：hash(key) → 定位目标节点 target
  ├─ 本地环视图命中 → 直连 target 发送 SET
  └─ 环视图过期 → 服务端返回 MOVED new_target → 客户端更新视图后重试
target 节点：
  1. 协议解析：校验命令与参数长度（超限报错）
  2. 归属校验：本节点是否仍拥有该 key（防迁移窗口期误写）
  3. 存储层：
     a. 若 key 已存在 → 覆盖值，刷新 LRU 最近使用位，更新 TTL
     b. 若 key 不存在 → 检查容量：满则触发 LRU 淘汰直至腾出空间
     c. 插入新条目（记录插入时间、过期时间戳）
  4. 返回 OK
```

### 4.2 读流程：GET

```
客户端 → 路由层定位 target → 发送 GET
target 节点：
  1. 惰性过期检查：若条目过期时间已到 → 删除该条目，按未命中处理
  2. 命中 → 刷新 LRU 最近使用位 → 返回 value
  3. 未命中 → 返回空值（区分"不存在"与"已过期"，均视为未命中）
指标：命中/未命中计数 → 命中率 = hits / (hits + misses)
```

### 4.3 过期判定与清扫（TTL）

- **惰性删除**：所有读路径（GET/EXISTS/TTL）在访问条目时校验 `expireAt <= now`，过期即删除并视为未命中——保证用户永远读不到过期数据。
- **主动清扫**：后台 goroutine 每 `-sweep-interval`（默认 500ms）遍历存储桶，删除已过期条目。为控制扫描成本，采用**分桶渐进式扫描**（每次扫描一个桶的子区间，一轮扫完全部桶），避免大容量下单次扫描卡顿。
- 清扫结果计入指标（expired_keys），并归还 LRU 容量。

### 4.4 LRU 淘汰流程

```
写入新 key 且 当前键数 >= 容量上限：
  loop:
    victim = 双向链表尾部（最久未使用）
    删除 victim（同时从 map 与链表中移除，若带 TTL 一并清理）
    键数--，容量释放
  until 键数 < 容量上限 或 链表为空（空则报错：容量为 0 或条目均被保护）
插入新条目到链表头部
```

- GET 命中、SET 覆盖 → 将条目移动到链表头部（O(1)）；
- 淘汰不区分"是否带 TTL"，统一按 LRU 次序；被清扫器删除的条目不参与淘汰。

### 4.5 路由与分片逻辑

- **哈希函数**：`crc32.ChecksumIEEE(key)` → 映射到 `[0, 2^32)` 环；
- **虚拟节点**：每个物理节点生成 160 个虚拟节点（`hash(nodeName + "#" + i)`），均匀分布到环上，缓解节点数少时的倾斜；
- **查找**：顺时针找到第一个虚拟节点，映射回物理节点；
- **单调性**：节点增减只影响环上相邻区间内的 Key，其余 Key 的归属不变；
- **客户端环视图**：客户端从任意节点拉取成员表（`MEMBERS`）后本地建环，后续请求直接路由；收到 `MOVED` 时更新视图。

### 4.6 扩容流程（节点加入）

```
1. 新节点 N 启动，向 seed 节点发送 JOIN(name, addr)
2. seed 校验唯一性 → 将 N 加入成员表 → 广播 MEMBERS_UPDATE 给所有节点（含 N）
3. 各节点（含 N）重建哈希环，计算本节点"不再拥有"的 Key 集合
4. 各旧节点对失主 Key 执行迁移 → 目标为环上新的归属节点（可能为 N）
5. 迁移完成 → 集群视图稳定 → N 开始正常服务
演示效果：扩容期间旧节点流量平滑下降，新节点承接约 K/N 的数据
```

### 4.7 缩容流程（节点离开）

- **优雅下线（LEAVE）**：
```
1. 目标节点 L 收到 LEAVE 命令（或控制台触发）
2. L 标记自己为 LEAVING：拒绝新写入，仍响应读取
3. 集群广播移除 L → 各节点重建环 → 计算 L 上 Key 的新归属
4. L 将自己的数据迁移到新归属节点
5. 迁移完成后 L 关闭监听，从成员表最终移除，进程退出
```
- **故障剔除（心跳超时）**：
```
1. 各节点连续 3 次心跳超时 → 判定 F 故障
2. 广播移除 F → 重建环
3. F 上的 Key 新归属节点无法从 F 拉取数据（F 已宕机）→ 这些 Key 暂时不可达
4. 设计取舍（演示版）：不可达 Key 在读取时按未命中处理，写入时直接重建；
   完整版可引入"源副本"机制，不在本次范围（详见 4.9 取舍说明）
```

### 4.8 迁移流程状态机

```
IDLE
 │  环变更事件（成员表变化）
 ▼
PREPARING   ① 记录变更前环与变更后环；② 枚举本节点需要迁出的 Key 集合
 │              （旧环归属自己 且 新环归属他人）
 ▼
MIGRATING   ③ 分页扫描本地存储（每批 100 条）
 │             ④ 逐条判断：新环归属 != 自己 → 发送 MIGRATE(key, value, ttlRemain)
 │             ⑤ 目标节点幂等写入；成功后在源节点删除该 key（先写后删，防丢数据）
 │             ⑥ 每批更新迁移进度（done/total）
 │  迁移期间环再次变化 → 中止 → 回到 PREPARING 按新环重算
 ▼
DONE        ⑦ 全部迁出完成 → 上报集群，进入 IDLE
异常恢复：源节点中途宕机 → 重启后重新进入 PREPARING，依据"新环归属"重新扫描，
         已迁出的 key 因目标节点幂等写入而安全（重复迁移无害）。
```

### 4.9 关键取舍与边界说明

| 场景 | 决策 | 理由 |
| --- | --- | --- |
| 故障节点上的数据 | 读取按未命中处理，不自动重建 | 保持机制简单可演示；副本/复制属于二期能力 |
| 迁移窗口期的并发写 | 写前校验归属（4.1 步骤 2），不归属则返回 MOVED | 防止旧环视图写入错误节点 |
| 迁移中的并发读写 | 先写目标、后删源节点；读请求仍可命中源节点 | 保证不丢数据、读最终一致 |
| 一致性级别 | 单副本、最终一致（迁移窗口内） | 演示版定位；强一致需引入共识/复制 |
| 数据全量在内存 | 是（纯内存缓存） | 缓存语义；重启丢数据可接受（缓存性质） |

## 5. 异常场景清单

| 编号 | 场景 | 处理 |
| --- | --- | --- |
| E1 | 客户端连接半包/粘包 | 协议层按帧长精确读取，不足则等待 |
| E2 | 非法命令/参数超限 | 返回 ERR 错误码 + 可读错误信息，连接不断开 |
| E3 | Key/Value 长度超限 | 按配置上限（默认 key ≤ 256B，value ≤ 1MB）拒绝 |
| E4 | 写满容量且无可淘汰条目 | 返回 ERR（容量不足） |
| E5 | 迁移目标节点不可达 | 迁移暂停并记录失败批次，目标恢复后重试；持续失败则触发故障剔除流程 |
| E6 | 迁移期间成员表再次变化 | 中止当前迁移，回到 PREPARING 按新环重算 |
| E7 | 节点重复注册（同名/同地址） | JOIN 时校验，冲突返回错误 |
| E8 | 服务端收到 MOVED 场景外的不归属写请求 | 返回 MOVED 并附正确归属节点 |
| E9 | 心跳超时误判（网络抖动） | 容忍阈值 3 次；恢复 PONG 后重置计数 |
| E10 | 优雅下线期间收到写入 | 返回 ERR（LEAVING），客户端重路由 |

## 6. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 单节点 SET/GET ≥ 5 万 ops/s（本机演示）；协议解析零额外拷贝尽量少 |
| 延迟 | p99 ≤ 5ms（本机回环）；路由层开销 ≤ 0.5ms |
| 可用性 | 单节点故障不影响其他节点服务；节点可动态增删 |
| 内存 | 每节点内存上限可配置，由 LRU 保证不超过上限（近似） |
| 可观测性 | 指标可查询（STATS / HTTP API），日志分级可配 |
| 可移植性 | 仅标准库，`go build` 单二进制，跨平台 |
| 代码规模 | Go 代码（不含测试）2000~2200 行；代码文件 21~24 个（目标 22） |

## 7. 验收标准摘要

见 [docs/07-测试与验收计划.md](07-测试与验收计划.md)，核心验收点：

1. 单节点 CRUD + TTL 过期 + LRU 淘汰行为正确；
2. 三节点集群下 Key 分布均衡（各节点键数偏差 < 20%）；
3. 加入新节点后，仅约 1/4 的 Key 发生迁移，迁移后所有 Key 可读；
4. 下线节点后，其余节点接管对应 Key（优雅下线场景数据不丢失）；
5. 控制台可实时展示拓扑、指标与迁移进度；
6. 代码规模满足 2000 < 行数 < 2200 且 20 < 文件数 < 25（不含测试）。
